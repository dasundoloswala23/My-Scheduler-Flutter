## Firebase

- macOS reuses the same iOS app registration (same bundle ID) — valid.

## Authentication

- Email/password: Firebase Auth, no native config needed.
- **Google Sign-In (iOS): NOT configured.** `google_sign_in` 7.x on iOS needs a `GIDClientID` (iOS OAuth client ID) in Info.plist or passed to `initialize(clientId:)`, plus the reversed client ID as a `CFBundleURLTypes` URL scheme. Neither exists, and `firebase_options.dart` has no `iosClientId`. Tapping "Continue with Google" on iOS is expected to fail. Needs the iOS OAuth client from the Firebase console (enable Google provider → download `GoogleService-Info.plist` → `CLIENT_ID` / `REVERSED_CLIENT_ID`). Cannot be completed from this environment.
- Apple Sign-In: offered on iOS only (`AuthService.supportsAppleSignIn`). Entitlement now present. The App ID's "Sign in with Apple" capability and the Firebase Apple provider must be enabled in the portal/console — the dev profile Xcode generated included the entitlement, which indicates the App ID capability is enabled; the Firebase side is not verifiable here.

## Notifications

- `flutter_local_notifications` 22.3.1. Initialisation does **not** request permission (`requestAlertPermission: false`); permission is requested when the first reminder is added (`ensureNotificationPermission` in `lib/features/task_detail/reminder_picker.dart`) with an explanatory dialog first. Matches the contextual requirement.
- Category with Complete / Snooze 10 min / Open actions is registered for iOS and macOS.
- **Issue fixed:** the Open action had no `foreground` option, so on iOS tapping it would not bring the app forward. Now `DarwinNotificationActionOption.foreground`.
- **Issue fixed:** `hasPermission()` always returned `true` on iOS/macOS, so a denial was never detected or explained. Now uses `checkPermissions()`.
- **Issue fixed:** denial messages now say exactly where to re-enable notifications (Settings › MyPlanScheduler › Notifications).
- Tap routing: `lib/features/home/notification_router.dart` opens the specific task's detail sheet (not just Home), including cold-start via `getNotificationAppLaunchDetails`.
- No remote push (APNs/FCM) is used; no `aps-environment` entitlement needed. Background modes not required for local notifications.

## Deep links / URL schemes

- No `CFBundleURLTypes`, no associated domains, no deep-link package. Deep links are **not implemented**; only notification → task routing exists.

## Data/performance notes

- Firestore is scoped per user (`users/{uid}/tasks` etc.) — no cross-user collection reads.
- Tasks are streamed as the user's full `tasks` collection (no pagination). Fine at hundreds of tasks; would need paging at thousands.
